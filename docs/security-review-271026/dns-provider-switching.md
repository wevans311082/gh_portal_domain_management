# Shared DNS provider switching

Required by the user on 30 October 2026 and added to roadmap item 5. Signup, customer and admin controls must launch one shared workflow for Cloudflare or WHM/platform DNS, including provider configuration and ResellerClub delegation updates. This feature is **in progress**, not enabled or accepted.

## Verified provider transport foundation

Cloudflare transport now bounds connection/read time to 10/30 seconds, disables redirects and performs one HTTP call per invocation. Transport/JSON errors and provider bodies are not exposed in exceptions. Mutation transport failures, redirects, server errors and unrecognized success envelopes retain uncertainty for the future operation reconciler. A successful envelope requires an actual boolean `success=true`; it is not by itself proof of completed DNS configuration or delegation. HTTP rejection classification is transport information, not authorization to replay a provider mutation.

`list_zones` accepts a validated domain and explicit 32-character account identifier, with exact name/account filters, match-all semantics and bounded page size/page input. `create_zone` can retain the selected account in its request and defaults discovery off. The old unscoped create signature remains compatible for the existing registration path; the new switching workflow must require an explicit captured account. No provider lookup or creation was performed against a live account during development.

Fifteen new transport checks cover scoped lookup/create requests, timeout/redirect bounds, no automatic mutation replay, sanitized timeout errors, HTTP rejection/uncertainty, malformed success envelopes and input rejection before HTTP. The combined transport/DNS CRUD/platform-cache run passes **39 checks**. Django and whitespace checks pass. The final full application suite passes **2,631 tests**, with the unchanged deployment assertion deselected.

The first full run found four old transport fixtures without real HTTP status values and an expectation that raw HTTP errors escape. Those fixtures now supply real status codes and verify the sanitized Cloudflare exception contract. The transport plus existing services/middleware suite passes **32 checks**; the final full rerun passes as recorded above. Account configuration UI, durable scopes/jobs and switch controls are not implemented by this transport increment.

Cloudflare documents account-scoped zone creation and notes that a new zone starts pending until the delegation/verification step is completed. This confirms that zone creation cannot be the final success state. See [Create Zone](https://developers.cloudflare.com/api/resources/zones/methods/create/). The lookup filters and pagination follow [List Zones](https://developers.cloudflare.com/api/resources/zones/methods/list/).

The WHM stage must operate on the domain's DNS zone and the platform/reseller nameserver configuration. cPanel distinguishes those settings from individual account nameservers; the legacy `modifyacct` helper is not evidence that a DNS-zone migration completed. See [cPanel nameserver setup](https://docs.cpanel.net/knowledge-base/dns/how-to-set-up-nameservers-in-a-cpanel-environment/) and [WHM DNS record API guidance](https://support.cpanel.net/hc/en-us/articles/1500000323641-How-to-add-a-DNS-record-to-a-domain-using-the-WHM-API).

## Authenticated public parent-DS observation

`domains.dns_parent_ds.read_parent_ds` now queries the exact ASCII/punycode domain's DS record through two fixed validating DNS-over-HTTPS services: [Cloudflare wire-format DNS](https://developers.cloudflare.com/1.1.1.1/encryption/dns-over-https/make-api-requests/dns-wireformat/) and [Google's RFC 8484 endpoint](https://developers.google.com/speed/public-dns/docs/doh). Domain input cannot choose an endpoint. Fresh HTTPS sessions use certificate verification, no environment credentials/proxies, bounded connect/read timeouts, no redirects and a streamed 65,535-byte wire limit. Queries request DNSSEC data and leave validation enabled.

Each resolver must return a matching, untruncated, successful DS question with an empty answer and no DS in the authority section, authenticated-data and recursion-available flags, an SOA from a proper ancestor, NSEC/NSEC3 denial evidence and matching unexpired parent signatures. Both must identify the same parent zone. Positive DS, NXDOMAIN, SERVFAIL, missing authentication/proofs, expired signatures, malformed/trailing wire data, redirects and oversized or expired HTTP responses require review. An empty record list by itself is never sufficient. See [RFC 4035 authenticated denial](https://www.rfc-editor.org/rfc/rfc4035.html#section-5.4) and [Google's secure transport/validation model](https://developers.google.com/speed/public-dns/docs/secure-transports).

The trust boundary is explicit: this adapter relies on the two validating resolvers' authenticated-data assertions over verified TLS. It does not claim local cryptographic chain validation. A receipt retains each resolver's name, parent, wire digest, observation time and remaining negative TTL. Validity is bounded by SOA/denial/signature TTLs, signature expiry, HTTP Age and network elapsed time; time spent waiting for the second resolver also consumes the first proof's validity.

Execution-input checks now bracket provider inventory rechecks with these public observations and reject an expired final proof. Their receipt can therefore record `parent_ds_verified: true`. It still records `ds_transition_verified: false` and `ready_for_mutation: false`: current authenticated absence cannot establish that all historic positive DS caches have expired after an external or managed DS change. Transition/cached-record settling and durable preflight/submission fencing remain required before writes. Unknown or unsupported denial forms stay in review; no unsigned result is guessed from an unavailable resolver.
