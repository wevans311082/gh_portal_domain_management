# Registrar organization-publication redaction

Withdrawing an explicit publication decision remains separate from provider confirmation and public-directory propagation. A tracked withdrawal creates one durable redaction job and one support case in the same transaction. Existing tracked withdrawals are backfilled by domains migration 0022; active consent and local-only withdrawals do not acquire jobs. Existing outcomes are preserved.

The processor locks the customer, domain, captured source association, decision and job. It requires the current decision to be the withdrawn decision, the original accepted registrar customer/scope, exact current remote roles and no unresolved contact replacement. Earlier purchases that have not produced a stable association wait for review. An obsolete decision cannot revoke a newer current consent implicitly.

Before mutation, the processor reads documented registrar consent and order/contact identity. Explicit false confirms provider revocation without mutation. Otherwise it commits the same order/customer/scope/contact IDs and a submission marker, rereads the association and sends those unchanged IDs with organization consent=false. It creates no new contacts, registration, transfer, invoice or payment and sends no external message. It neither bypasses registrant authorization nor opts out of transfer locks.

An acknowledgement means awaiting confirmation. A lost response or interrupted worker is uncertain and never triggers another mutation. Later runs only read provider state. Explicit `registrantOrgConsent=false` with applicable consent and matching identity/roles records provider confirmation; null, missing, malformed or true values do not. A marker independently blocks replay even if a status were reset incorrectly. Provider messages, credentials and raw contact details are not copied into job/audit records.

Background processing uses leases, hard/soft task limits, a shared 20-operations-per-minute registrar quota and bounded 100-record/eight-second dispatch. Missing limiter storage defers work before constructing a provider client. Review/read failures back off five minutes; broker failures retain durable work. Eager task settings cannot perform provider work during an HTTP withdrawal. Customer withdrawal requests have shared body/rate limits.

A contact replacement already submitted with publication consent may complete after withdrawal if the owner verifies its exact provider outcome and all identity/contact/IRTP gates pass. That records actual identity truth without reinstating consent, then allows the separate redaction job to run. Changes not submitted before withdrawal cannot retain the old affirmative snapshot.

The private publication-consent page distinguishes queued, awaiting, uncertain, association-review and provider-confirmed outcomes. It never claims the support case is closed or that public WHOIS/RDAP caches have propagated. Support remains available for anomalous or unresolved provider outcomes. No automatic blind retry/override command is provided.

The documented provider read contract is [order details](https://www.resellerclub.com/help/article/Get-Domain-Registration-Order-Details-by-Order-ID-Using-the-API); mutation uses [modify domain contacts](https://www.resellerclub.com/help/article/Modify-Domain-Contacts-Using-the-API), reviewed 28 October 2026. These contracts distinguish registrar organization consent from broader identity, eligibility, privacy-service and public-directory checks.

Verification includes durable submission, lost-response replay prevention, foreign IDs, withdrawn in-flight contact replacement, ownership, typed consent values, migration preservation and customer progress. The isolated 0020-to-0022 upgrade exercises historical model states; ten desktop/mobile browser states pass accessibility/overflow checks, with a mobile confirmed-state screenshot inspected. Tests use isolated SQLite and mocked providers. No production migration, live mutation or PostgreSQL locking verification has occurred.
