# Individual and registrar validation requirements

Added 28 October 2026 following the requirement that individuals can be validated without being businesses. This extends roadmap item 3 and the registration, transfer, contact-change and domain-operation workflows. These are implementation requirements; this document does not claim the current application complies.

## Current code findings

- `apps/domains/forms.py`: saving an individual contact sets `registrant_validation_status=validated` without external verification. Companies House success sets the same status, although this is a business-record check rather than registrar verification.
- `apps/domains/forms.py`: domain ordering relies on this combined status, so its meaning affects order eligibility.
- `apps/domains/models.py`, `DomainContact.as_resellerclub_payload`: missing contact values are replaced with invented address, city, postcode or phone values, and overlong values are silently truncated. These substitutions must be removed from the registration path. Required accurate data must be requested from the customer.
- Existing status values cannot establish historical registrar verification. Preserve them as legacy local review evidence, with registrar status unknown until supported by provider evidence.

Missing/mismatched binding is a failure, not approval. The local order/contact snapshot is rechecked under row locks after the network read. Evidence is explicitly domain-order-bound with retained history, provider source/reference, checked time and 15-minute freshness expiry. ### Bounded status-check and resend workflow

Customer domain pages now provide CSRF-protected POST actions to queue a status check and, for current pending/suspended .com/.net/.org evidence, request a registrar verification email. Neither action accepts a recipient override or calls the provider during HTTP handling, including with Celery eager mode enabled. Ownership is checked before admission. Invalid requests return a helpful error page; cooldowns return 429 with Retry-After, cache/store failures return generic 503, and an uncertain resend returns 409 requiring provider review. Responses and source pages do not reveal private provider errors or audit reasons.

`VerificationAction` and the singleton admission lock (`domains/0012_verification_action_queue.py`) provide durable UUID-keyed requests, one open request per order/action, 60-second refresh and 300-second resend cooldowns, and a 500-open-action global capacity. Shared early IP/global/account limits bound submission and form bodies. Admission and its audit event commit together. A broker failure leaves a queued row; application beat configuration dispatches up to 100 queued actions every minute. Workers claim rows under a lock; duplicate deliveries are no-ops. Eager HTTP execution is explicitly avoided. No server process or deployment configuration was changed.

Workers recheck account activity, ownership, domain linkage and contact snapshot. Every resend first reconciles provider state and proceeds only on current pending/suspended evidence. The local job, order, contact, domain and actor are locked and rechecked through the bounded provider POST. A literal provider false means failed; an exception after entering the mutation, unrecognised result, or expired resend lease becomes unknown and is never automatically resent. Expired read-only refresh jobs fail without sending email. Task limits and three-minute leases bound running-state recovery; audit records contain local IDs, operation and safe outcomes rather than provider payloads. PostgreSQL claims lock only the job row despite nullable related joins.

The resend endpoint follows the [documented POST contract](https://manage.resellerclub.com/kb/answer/2010), checked 28 October 2026. The HTTP client now preserves literal JSON booleans instead of converting them into contact identifiers. Contact creation additionally rejects boolean, fractional and malformed IDs without echoing raw provider responses; stored malformed IDs require review.

An uncertain result can be resolved from a trusted operator shell using `python manage.py resolve_verification_action --action-id <id> --owner-id <active-owner-id> --outcome sent|not-sent --reason <review-reason> --provider-reference <case-reference>`. The command requires an active owner for audit attribution, a bounded reason and provider case reference. Shell access is the operator authentication boundary; supplying an owner ID is not an HTTP login/MFA mechanism. Resolution is audited atomically, sends no email and never marks the contact verified. An uncertain resend continues to appear on the customer page even after newer refreshes, and the resend button is hidden until review is resolved.

### Automatic read-only reconciliation

The application scheduler now scans linked completed .com/.net/.org orders for active account owners and active/expired/suspended domains. Each invocation examines at most 100 orders and stops admission after an eight-second monotonic processing budget, committing partial progress. A composite order status/TLD/ID index supports selection. Migration `domains/0013_verification_scan_cursor.py` adds the cursor, explicit automatic-job flag, availability time and index; it excludes the unrelated DomainOrder choices drift.

Fresh evidence is skipped, and unchanged pending/cooling-down work is not duplicated. Automatic admission uses a 15-minute cooldown, including after failure, and shares the 500-open-action capacity with customer requests. A full queue pauses the cursor rather than skipping orders. Automatic actions are explicitly attributed to the system, not to the customer. The internal automatic path accepts refresh only, and the worker rejects automatic resend jobs. Customer POST data cannot select automatic identity. Inactive owners, changed ownership/contact snapshots, unlinked contacts and mismatched stored extensions do not produce provider work.

Worker admission now shares a fail-closed budget of **30 verification jobs per minute** across customer and automatic jobs. This is a local workload limit, not a claim about the provider's account-specific rate allowance. 1. Explicitly support an individual and an organisation as registrant types. Do not infer identity solely from a blank company field. Individuals need accurate name, contact details and any applicable eligibility data; they do not need a company number or Companies House verification. Sole traders and overseas organisations must not be forced through a UK incorporated-company-only flow.
2. Show separate states for portal email, contact completeness/format, local identity or business review, registrar email verification and TLD eligibility. A local staff approval, Companies House match or portal email link must never mark registrar verification complete. Do not describe form validity as verified personal identity.
3. Record the subject/contact version, source, checked time, relevant domain/TLD and evidence reference for verification outcomes. Changes to relevant identity, address, email or eligibility fields invalidate the corresponding checks; historical evidence remains auditable. Reconcile existing provider contacts instead of assuming that a stored contact ID proves verification.
4. Use a tested per-TLD contact policy for contact types, individual/organisation fields, lengths, required eligibility attributes and agreements. No invented address/phone data, silent truncation or blanket company placeholder. Provider documentation has TLD-specific exceptions, including omission of company for individual .ES contacts. Unknown or unsupported policies require review before a paid provider operation.
5. Treat provider eligibility validation and email verification as different operations. The documented `contacts/validate-registrant` API checks specified eligibility criteria; its successful result is not general identity or email verification. Persist only evidence actually returned by the relevant provider operation.
6. Permit registration to enter a genuine post-registration verification state where the registrar workflow requires it. Show pending action, provider-supplied deadline, last checked time and suspension/recovery guidance. Do not block registration on a verification step that can only begin after registration. Resend, reconciliation and contact updates need permissions, bounded retries and duplicate protection.
7. Apply checks server-side to registration, transfer, bulk operations and contact replacement, including all selected contact roles. Recheck current contact version and TLD policy before provider submission. An unsupported policy or provider error must not become a successful verification result.
8. Request extra identity evidence only where a documented registry/provider requirement or a separately defined local review policy requires it. Keep sensitive evidence out of logs, public/customer timelines and ordinary staff views. Define access and retention before collecting documents or identity numbers.

## Provider requirements checked

- ResellerClub's [Add Contact API](https://manage.resellerclub.com/kb/answer/790) supports natural persons and organisation-specific attributes. ## Required verification before completion

- An individual with valid contact data progresses without company fields or a Companies House request; malformed/missing required contact data is rejected without fabricated substitutions.

- Mock provider responses for pending, successful, rejected, unknown, stale and unavailable checks. Confirm actual API contracts with a provider test account before claiming end-to-end provider verification; do not contact production providers from automated tests.
- Contact edits invalidate relevant results; legacy rows remain explicitly unconfirmed; concurrent edits and repeated submissions cannot reuse stale approval or duplicate a paid action.
- Verify role restrictions, customer ownership, CSRF, audit redaction, evidence access, resend throttling and retry handling.
- Browser checks cover individual/business forms, helpful errors, pending/deadline states, long content, keyboard use and contrast. Workspace panels distinguish missing, not applicable, pending and verified states in text as well as colour.


## Immutable registrar contact bindings - 28 October 2026

ResellerClub's [Modifying Contact Details API notice](https://manage.resellerclub.com/kb/answer/791), rechecked 28 October 2026, says contact modification was deprecated from 1 December 2016 and directs clients to create new contacts and associate them with domains. The registration/transfer path now creates immutable bindings instead of calling `contacts/modify`; the old client method explicitly refuses network access.

Bindings are scoped by local contact, provider endpoint/reseller fingerprint, customer ID, contact type and a SHA-256 digest of the exact normalized add-contact payload. General and UK contacts cannot overwrite one another. An unchanged general contact can be reused across reviewed general-contact TLDs; edits create a new version. Legacy `registrar_contact_id` values are preserved for historical orders and are never blindly adopted or overwritten by new creation.

A durable database reservation commits before the provider POST. Nested business transactions are rejected before any provider mutation. Concurrent/in-flight requests, process loss, timeouts and malformed creation responses cannot automatically start another POST for the same binding. Uncertain results require reconciliation. Successful IDs are strictly positive ASCII numeric values of at most 19 digits; provider response bodies and original contact payloads are not stored in the binding. A mid-request edit preserves the known remote version but prevents its attachment as the current contact.

New registration and transfer records snapshot the provider scope and the actual IDs submitted for each role. Verification reads the order-specific registrant ID, validates provider environment, and records that remote contact and scope in its evidence. A changed order binding invalidates evidence and cancels queued actions before a provider read or resend. Existing orders without snapshots retain the historical legacy-ID fallback; they do not acquire a falsely inferred contact type.

### Reconcile an uncertain contact creation

This is an operator attestation, not an automated identity or registrar verification. Stop any potentially running creation worker first. Review the provider account/environment, customer, contact type, complete original submitted details and provider case history. Match the exact original payload digest; a hash alone is not proof of matching contact details. If the original details cannot be established, leave the binding blocked and escalate to provider support. Do not clear reservations or retry creation on a timeout alone.

After provider-side confirmation, an active owner can run `manage.py resolve_registrar_contact --binding-id ID --owner-id ID --remote-id ID --confirmed-payload-digest SHA256 --provider-reference CASE --reason "Reviewed matching original provider contact"`. This command makes no provider request, records an audit event atomically, cannot overwrite a ready binding and refuses a creating reservation younger than 15 minutes. It associates only the reviewed immutable contact; it does not change domain ownership, submit a registration, resend email or mark any verification passed. When no contact was created, obtain a confirmed matching contact through the registrar's supported process before associating it; this command deliberately provides no blind reset/retry switch.

The application tests use isolated databases and mocked provider contracts. Live PostgreSQL concurrency, funded provider sandbox registration and provider support reconciliation remain external verification; no production registrar contact or domain was changed. Broader contact-replacement/IRTP workflows and additional TLD eligibility adapters remain roadmap work.
