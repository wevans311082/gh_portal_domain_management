# Bulk domain operations — implementation in progress

Roadmap item 5 requires lock, auto-renew, nameserver and contact changes with a preview, applicable costs and per-domain job results. Every item must be authorized independently; unsupported items must be explained; repeated submission must retain completed changes; partial failures need selective safe retry. Transfer initiation and EPP disclosure remain separate sensitive workflows. No provider access or production migration has occurred.

## Implemented preview foundation

`apps/domains/bulk_preview.py` normalizes an explicit target rather than a toggle, bounds a selection to 100 distinct integer IDs, and accepts only the four named operations. Nameservers are canonicalized and checked for distinct valid hostnames before per-registry bounds are evaluated. Contact roles must exactly match the domain's reviewed policy and every proposed contact must belong to the customer. Publication choice is validated separately from contact eligibility.

The service rereads and locks the active ordinary customer and independently filters each selected domain by ownership. Foreign and missing IDs return the same unavailable message without domain names. Owned unsupported or held domains have per-item explanations; they do not prevent the rest of the preview. Unknown/prepared extensions remain held under the existing shared workstream catalogue. There is no new per-TLD KYC system.

For provider operations it requires a captured accepted registrar association, current provider scope and no open registrar/contact-change review. Private snapshots capture the actual domain, owner, provider association, policy, requested target and relevant current state/contact digests. Snapshots are not displayed as provider approval. A cached lock flag is never treated as a completed provider operation. Disabling local auto-renew remains possible during registrar review. Enabling it uses existing renewal restrictions.

The preview performs no provider HTTP, evidence/consent write, queue publication or domain mutation. It does not calculate or authorize a charge. Contact-holder changes that need a separate registry transaction must remain within the reviewed workflow. No HTTP route or production batch execution is enabled by this foundation.

Verification: **15 focused tests pass**, covering invalid/sensitive actions, selection bounds and duplicate IDs, typed targets, namespace restrictions, mixed ownership without disclosure, provider-client prohibition, no audit/change/evidence writes, registrar review, nameserver normalization/bounds, owned contact roles, snapshot freshness and customer deactivation.

## Required execution and UI work

- Commit a submission marker before provider mutation. Interrupted or ambiguous mutations become review/observation states, never automatic fresh POSTs. Completed items remain completed on replay. Retry only selected items proven not to have crossed the mutation boundary.

## Reservation and local-preference increment

Migration `domains.0029_bulk_domain_reservations` adds a unique domain/item reservation. Confirmation creates reservations atomically with queued items and its audit. Overlapping previews cannot both confirm the same domain; exact confirmation replay preserves its existing reservation. Reservations have no automatic expiry: queued, preparing, submitting, awaiting and unknown work retain the slot. A failed item with a submission marker also retains it. Release rereads locked database state, so a stale object labelled completed cannot release uncertain work. Only completion or proven pre-submission failure/cancellation permits cleanup.

The shared registrar review guard now sees reservations, and standalone contact admission checks the same slot while holding the customer/domain locks. Internal execution may exclude its own item when rechecking the registrar association; this is not a customer-controlled exemption. This preliminary integration is **not** a claim that legacy lock/nameserver requests already in flight are fully serialized: their check-to-HTTP race, local preference cancellation semantics and admin domain edits still need integration before bulk execution is exposed.

`bulk_execution.execute_local_preference` executes only an admitted local auto-renew item. In one transaction it locks customer/domain/batch/item, rechecks current authority, manifest, reservation and the exact preview snapshot, saves the preference, records completion and releases the slot. Duplicate delivery retains completion. Preflight failure records a safe explanation and frees only its own slot; audit failure rolls back the preference, item state and reservation together. This does not promise future payment or registrar renewal and performs no provider HTTP.

## Bounded dispatch increment

`bulk_jobs.py` registers a bounded dispatcher and per-item worker. Execution is explicitly gated by the Boolean Django setting `DOMAIN_BULK_EXECUTION_ENABLED`, defaulting to false while this feature remains unfinished. Eager mode cannot publish or dispatch jobs from confirmation. No periodic beat schedule is enabled yet. Confirmation registers publication callbacks only after its records, reservations and audit commit; broker failure leaves the same durable item for later delivery.

The dispatcher attempts at most 100 due items per call, with an eight-second loop budget and Celery 20/30-second soft/hard limits. Publication backoff is separate from execution availability: advancing `dispatch_after` does not prevent a delivered worker from claiming the item. Broker acknowledgement failure never allocates a replacement request. Worker claims have a separate UUID/lease from provider submission tokens and read-observation leases, so an old finisher cannot clear a new claim or change provider identity. Active leases and unconfirmed history are excluded.

Workers apply customer (10/minute) and global (20/minute) item budgets through the shared cache, fail closed when the store is unavailable, and defer on quota exhaustion. Customer denial is checked before consuming global provider-work capacity. The 210/240-second worker limits fit inside a five-minute dispatch lease. Actual execution routes through the previously verified local auto-renew, linked contact, fenced lock/nameserver submission or read-only observation services. Contact parents project their existing child's result rather than submit again. Completed rows are never restarted.

An interrupted submitting item older than 15 minutes with no live dispatch/observation lease becomes unknown with an audit; its submission marker and reservation remain. It may proceed only through observation/review, never a fresh mutation. Worker exceptions before submission can stop safely; a provider marker or linked child instead retains uncertainty. Error bodies are not stored. Final dispatch updates are token-checked and retain action-specific observation delays. This is application scheduling logic, not a deployment change or a claim of live broker/worker readiness.
